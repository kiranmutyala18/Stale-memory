# StaleMem

[![CI](https://github.com/kiranmutyala18/Stale-memory/actions/workflows/ci.yml/badge.svg)](https://github.com/kiranmutyala18/Stale-memory/actions/workflows/ci.yml)
**[Live demo](https://huggingface.co/spaces/white0404/stalemem-demo)** | Python | pydantic | pytest | GitHub Actions

An evaluation framework for assistant memory: schema-validated test cases, three memory formats,
a rule-based scoring engine, CLI, and tests with CI that fails if the committed results stop reproducing.
Also see its sibling project, [CodeMix-Personalization](https://github.com/kiranmutyala18/CodeMix-Personalization).

A small benchmark for one question: **when an assistant remembers something about you, does it know when to
trust it, when to check it, and when to drop it?**

Most memory work asks what to store. This asks what to do with a fact once time has passed. An assistant that
says "good luck with your interview tomorrow" three weeks after the interview, or plans a dinner for a guest
who left last week, is worse than one with no memory at all.

## Layout
```
stalemem/schemas.py   Case model + label/horizon consistency validators
stalemem/cases.py     24 hand-written seed cases
stalemem/prompts.py   three memory formats -> system prompts
stalemem/scoring.py   pure rule functions (has_check, outcome) + run()
stalemem/dataset.py   validation and JSONL export
stalemem/demo.py      static results page builder
stalemem/cli.py       `stalemem <command>`
tests/                pytest suite; CI in .github/workflows/ci.yml
```
The replies in `data/responses/` were generated by independent Claude runs, each seeing only its own prompt file.

## Run
```bash
pip install -e ".[dev]"
pytest -q            # 18 tests: schema validators, scorer rules, pipeline round-trip
stalemem validate    # check cases, write data/cases.jsonl
stalemem prompts     # write data/prompts/*.jsonl (3 formats x 24 cases)
stalemem score       # data/responses/*.jsonl -> data/results.json
stalemem demo        # embed everything into demo/index.html (static page)
stalemem all         # all of the above; CI checks it reproduces the committed files
```

## The four behaviours

| Gold action | Situation | What a careful assistant does |
|---|---|---|
| `use` | Stable or recent fact | Answers with it directly. Asking is an unnecessary check. |
| `verify` | Old fact that tends to change | Answers, but confirms the fact or hedges first. |
| `update` | A newer entry replaces an old one | Uses the newer fact and never the old one. |
| `expired` | Fact tied to an event that has passed | Does not treat it as current; may ask how it went. |

## Research questions
1. **RQ1** - Do current LLMs act on memory timestamps, or treat every stored fact as equally true?
2. **RQ2** - Does adding timestamps and a short "check old, volatile facts" instruction change behaviour?
3. **RQ3** - What does over-correction cost? Checking everything is annoying, so unnecessary verification
   is measured as carefully as stale errors.

## Design
- **Cases** (`data/cases.jsonl`): 24 hand-written, 6 domains (work, location, family, education, health, plans)
  x 4 gold actions. Facts are synthetic. Query date is fixed at 2026-11-14.
- **Fact classes:** `stable` (never expires), `slow` (assumed 365-day horizon), `fast` (90 days), `event`
  (expires on its event date).
- **Validation:** `stalemem validate` checks that every gold label is consistent with those horizons, that update
  cases have a newer entry, and that expired cases really have a past event date.
- **Metrics:** stale-fact error rate, update accuracy, unnecessary-verification rate, expired-fact
  error rate.

## First results (24 cases x 3 formats = 72 replies; one model family; one reply per prompt)
| Cases handled well | Plain notes | Dated notes | Dated + guidance |
|---|---|---|---|
| use (6): answer directly | 6 | 6 | 6 |
| verify (6): check an old fact | 1 | 5 | 6 |
| update (6): use the newer fact | 6 | 6 | 6 |
| expired (6): drop a past event | 6 | 6 | 6 |
| Outdated fact used as current (of 18) | 5 | 0 | 0 |
| Unneeded checks on stable or recent facts (of 6) | 0 | 0 | 0 |

- Without dates, old facts are used as if they were fresh (5 of 5 silent assumptions were on `verify` cases).
- Dates fix most of it; a short guidance paragraph closes the last gap. That format states the rule, so it
  measures instruction-following.
- No over-checking appeared, but 6 cases per format is a small test.
- **Update and expired are too easy as written:** the notes carry their own cues, so they score 6/6 even without
  dates. The next version needs implicit staleness.
- Scoring: rules first, then all 72 replies read by hand. Rule fixes changed 5 of 72 outcomes (applied to all
  formats equally); no per-reply overrides. Two borderline calls are explained on the results page.

## Caveats
- The horizons (365 and 90 days) are working assumptions, not measurements. Reasonable people would pick
  different numbers, so the label check shows internal consistency, not truth.
- 24 cases is a seed set. Do not draw statistical conclusions from it.
- Stale and fresh markers are keyword heuristics and will miss paraphrases; all 72 replies were read by hand to check them.
